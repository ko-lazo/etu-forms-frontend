# Формы: слои и жизненный цикл

Описание работы с формами и словарь терминов в коде

## Связанность с дочерними сущностями

Зависимость между ними односторонняя:

```
Form  ──────►  FormResponse
```

Форма о своих ответах ничего не знает. Ответ без формы не существует.
Так же устроены и фичи: `features/forms` не импортирует `features/form-responses`
ни разу.

## Слои

```
                     ┌───────────────┐
                     │    schema     │  
                     └───────┬───────┘
                             │
        ┌─────────────────┬──┴───────────────┐
        ▼                 ▼                  ▼
┌───────────────┐ ┌───────────────┐  ┌───────────────┐
│  features/ai  │ │    editor     │  │    runtime    │
│  генерирует   │ │ строит схему  │  │ заполняет по  │
│     схему     │ │               │  │ схеме         │
└───────┬───────┘ └───────────────┘  └───────┬───────┘
        │ готовая схема   ▲                  │
        └─────────────────┘         FormInputStorage
                                  (ввод данных в фому)
                                             │
                                             ▼
                                     ┌───────────────┐
                                     │ form-responses│
                                     │ хранит ответ  │
                                     └───────────────┘
```

`editor` и `runtime` не знают друг о друге: оба читают `schema`. Единственная
точка соприкосновения - предпросмотр в конструкторе, который запускает `runtime`
без сохранения ввода данных в форму.

`ai` лежит отдельной фичей и тоже не знает про `editor`, 
компонент `FormEditor` переводит её в модель редактора (`schemaToEditorPages`) 
и заменяет страницы. Ответ ИИ конструктора применяется сразу: по сообщению модели 
не видно, что именно изменилось, поэтому показывать её стоит уже в полях. 
В БД схема уходит только с общим сохранением формы, а откатывается
общим сбросом изменений через UI.

`runtime` не знает, куда уходит ввод: он объявляет порт `FormInputStorage`,
а реализацию поверх API даёт `form-responses`.

## Жизненный цикл заполнения

| # | Что происходит                           | Где это лежит                                               |
|---|------------------------------------------|-------------------------------------------------------------|
| 1 | Форма рендерится по схеме                | `components/form/runtime/Renderer.vue`, `FieldRenderer.vue` |
| 2 | Пользователь вводит данные               | `useFormRuntime.setValue` → `storage.save`                  |
| 3 | Поля показываются и прячутся по условиям | `runtime/evaluate-condition.ts` → `visiblePages`            |
| 4 | Пользователь нажимает «Отправить»        | `useFormRuntime.submit`                                     |
| 5 | Ввод проверяется, показываются ошибки    | `runtime/validate-input.ts`, `InputRejectedError`           |
| 6 | Ответ сохранён как отправленный          | `useFormResponseStorage.submit` → `submittedAt`             |

Шаг 2 попутно решает сценарий «заполню позже»: `storage.save` сохраняет ввод как
`FormResponse` без `submittedAt` и подставляет в адрес `?r=<id>`, по которому
можно вернуться. Отсюда же индикатор «Сохранение… / Черновик сохранён».

Шаг 5 двухступенчатый. Обязательные поля проверяются на клиенте мгновенно
(`validateRequiredFields`), всё остальное - типы, диапазоны, допустимые
варианты, email - проверяет backend и возвращает 400 со списком
`{ field, code, params }`; реализация хранилища переводит его в
`InputRejectedError`, и `runtime` показывает ошибки у полей, ничего не зная
о формате ответа API.

## Словарь

| Слово        | Значение                                             | Где встречается                            |
|--------------|------------------------------------------------------|--------------------------------------------|
| `schema`     | описание формы: страницы, элементы, условия          | `forms/schema`                             |
| `element`    | поле формы в схеме                                   | `schema/form-schema.ts`                    |
| `condition`  | правило видимости элемента или страницы              | `schema/condition.ts`                      |
| `input`      | введённые пользователем значения                     | `forms/runtime`                            |
| `answers`    | имя поля ввода в теле `FormResponse`                 | только `useFormResponseStorage`            |
| `response`   | сущность `FormResponse`                              | `form-responses`                           |
| `draft`      | статус формы: не опубликована                        | `FORM_STATUS.DRAFT`                        |
| `transition` | переход статуса формы: publish, archive и обратные   | `FORM_TRANSITION`, `useFormLifecycle`      |
| `editor`     | конструктор формы                                    | `forms/editor`, `components/form/editor`   |
| `runtime`    | заполнение формы по схеме                            | `forms/runtime`, `components/form/runtime` |
| `prompt`     | описание формы словами, запрос к ИИ                  | `features/ai`                              |
| `limit`      | остаток суточной квоты запросов к ИИ                 | `GET /ai/limit`, `features/ai`             |

Отдельно про `input` и `answers`: данные, которые вводит пользователь, называются
вводом, потому что в этот момент форме неизвестно, станут ли они ответом. 
Переходят в `answers` они ровно в одном месте - при отправке в API:

```ts
await responsesApi.save({ answers: input, metadata: {}, submittedAt: null })
```
